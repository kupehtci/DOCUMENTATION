# SonarQube Scanner Configuration

SonarQube scanner behavior can be configured using a `sonar-project.properties` file defining all the properties that the project has to be analyzed with SonarQube. 

## `sonar-project.properties` Configuration file

This file is placed in the root of the project (Same level as .git for example). 
Its a raw text file with a `key=value` format (one per line) with comments using `#` that defines all the configuration of the scanner. 

Properties can also be passed to the scanner as `-D` command line arguments (`-Dsonar.projectKey=...`) or as environment variables, overriding the ones defined in the file. 

## Project identification

| Property                   | Description                                                 | Example                  |
| -------------------------- | ----------------------------------------------------------- | ------------------------ |
| `sonar.projectKey`         | Unique identifier for the project in SonarQube              | `mi-empresa:mi-proyecto` |
| `sonar.projectName`        | Name shown in the SonarQube UI.                             | `Mi App`                 |
| `sonar.projectVersion`     | Versión of the project                                      | `1.2.3`                  |
| `sonar.projectDescription` | Description of the project. Not supported in `dotnet`.      | `Backend of the app`     |
| `sonar.projectBaseDir`     | Root of the project.                                        | `.` o `/app`             |
| `sonar.projectDate`        | Forces the analysis date instead of using the current date. | `2024-01-15`             

## Server connection & authentication

Mandatory parameters to connect the scanner to the SonarQube server (`sonar.host.url`, `sonar.token`) are detailed in [[SonarQube - CI-CD Parameters]], since they are normally injected by the CI/CD platform instead of being committed in the properties file. 

## Analysis scope

Defines which files are analyzed as source code, tests, or excluded from the analysis: 

| Property                    | Description                                                                                   | Example                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------- |
| `sonar.sources`              | Path(s) with the main source code to analyze. Relative to `sonar.projectBaseDir` or absolute.  | `src`                            |
| `sonar.tests`                | Path(s) with the test source code.                                                              | `test`                           |
| `sonar.sourceEncoding`       | Character encoding used to read the source files.                                               | `UTF-8`                          |
| `sonar.inclusions`           | Patterns of files to include in the main code analysis (all files included by default).         | `src/**/*.js`                    |
| `sonar.exclusions`           | Patterns of files to exclude from the main code analysis.                                       | `**/*.spec.js,**/node_modules/**` |
| `sonar.test.inclusions`      | Patterns of test files to include.                                                              | `**/*.spec.js`                   |
| `sonar.test.exclusions`      | Patterns of test files to exclude.                                                               | `**/node_modules/**`             |
| `sonar.coverage.exclusions`  | Patterns of files excluded from coverage calculation, without excluding them from the analysis. | `**/*.dto.ts`                    |
| `sonar.cpd.exclusions`       | Patterns of files excluded from duplication (copy-paste) detection.                             | `**/generated/**`                |

## Coverage & test execution reports

The scanner does not compute coverage itself, it imports the reports generated by the language's own test/coverage tooling. The path(s) property depends on the language: 

| Property                            | Language / Tool                          |
| ------------------------------------ | ------------------------------------------ |
| `sonar.javascript.lcov.reportPaths` | JavaScript / TypeScript (`lcov.info`)     |
| `sonar.python.coverage.reportPaths` | Python (`coverage.py`)                    |
| `sonar.coverage.jacoco.xmlReportPaths` | Java (JaCoCo XML report)               |
| `sonar.cs.opencover.reportsPaths`   | .NET (OpenCover)                          |
| `sonar.cs.vscoveragexml.reportsPaths` | .NET (Visual Studio coverage XML)       |
| `sonar.testExecutionReportPaths`    | Generic test execution report (pass/fail/skip), independent of coverage. |

## Multi-module projects

| Property        | Description                                                                 | Example         |
| ---------------- | ------------------------------------------------------------------------------ | ----------------- |
| `sonar.modules`  | Comma separated list of sub-modules, each analyzed as an independent sub-project sharing the same analysis. Each module can override the above properties prefixed with `<moduleKey>.`. | `module-a,module-b` |

## Branch & Pull Request analysis

Properties used to analyze branches and pull requests (`sonar.branch.name`, `sonar.pullrequest.key`, `sonar.pullrequest.branch`, `sonar.pullrequest.base`) are detailed in [[SonarQube - CI-CD Parameters]] and [[SonarQube - Pull requests analysis]]. 

## Source Control Management (SCM)

| Property                  | Description                                                                           |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| `sonar.scm.provider`       | Forces the SCM provider to use (`git`, `svn`...) instead of auto-detecting it.        |
| `sonar.scm.disabled`       | `true` \| `false`. Disables the SCM sensor (blame information will not be collected). |
| `sonar.scm.forceReloadAll` | `true` \| `false`. Forces reloading the SCM blame data for every file, not only the changed ones. |

More details in [[SonarQube - SCM]]. 

## Logging & verbosity

`sonar.verbose` and `sonar.log.level` are detailed in [[SonarQube - CI-CD Parameters]]. 

## Quality Gate

| Property                  | Description                                                                                     | Example |
| --------------------------- | --------------------------------------------------------------------------------------------------- | --------- |
| `sonar.qualitygate.wait`   | `true` \| `false`. Makes the scanner poll the server and wait until the Quality Gate status is computed, failing the build/pipeline step if not passed. |  `true` |
| `sonar.qualitygate.timeout` | Number of seconds to wait for the Quality Gate result before timing out.                         | `300`   |

More details in [[SonarQube - Quality Gate]]. 

## Links

Metadata links shown in the SonarQube UI project page: 

| Property             | Description                          |
| ---------------------- | --------------------------------------- |
| `sonar.links.homepage` | URL of the project's homepage.        |
| `sonar.links.ci`       | URL of the CI/CD pipeline.            |
| `sonar.links.scm`      | URL of the source code repository.    |
| `sonar.links.issue`    | URL of the issue tracker.             |

## Working directory & scanner behavior

| Property                        | Description                                                                                | Example       |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------- |
| `sonar.working.directory`         | Temporary folder used by the scanner to store intermediate analysis data.                     | `.scannerwork`  |
| `sonar.analysisCache.enabled`     | `true` \| `false`. Enables the analysis cache to speed up consecutive analyses of the same branch. | `true`        |
| `sonar.scanner.metadataFilePath`  | Path where the scanner writes the `report-task.txt` file, used by tools like the Azure DevOps task to build the dashboard link and poll the Quality Gate. | `.scannerwork` |
## Plugins

Additional properties are exposed by installed plugins, for example the OWASP Dependency Check plugin ([[SonarQube - Dependency Check]]), whose properties are detailed in [[SonarQube - CI-CD Parameters]]. 

## Azure DevOps SonarQubePrepare task

In Azure DevOps this configuration can be injected to the `SonarQubePrepare` task using the file in the project or directly by the `extraProperties` task' variable.
